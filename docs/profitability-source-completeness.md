# Profitability source completeness

Prepared against production commit `9d151045db9af0db5b25e5b824be6f653b631ca6`, deployment `dpl_AyvKpX9edsBYsx3AP9h1jW5hgvyF` (app.rms.rest). This patch changes reporting code only. No migration, data reconciliation, setting change, deployment, or automatic evidence conversion is included.

## Behavior

- Read salary periods, employees (including inactive employees), and service charge with stable pagination. Errors, null responses, and exhausted read limits fail the report instead of returning partial totals.
- Use salary_gross only in the profitability report. Observed zero stays zero; net balances, advances, payments, current salary rates and official-day estimates cannot substitute for accruals. Employee/period identities and duplicate employee-month rows are checked. The existing management allocation policy remains in place.
- Consume reviewed component records for every selected month. DSMF is an explicit supported branch component, alongside Partner Fee. Existing provenance, identity, collision, duplicate, and stale-input checks still apply. No inferred employee matching or October amounts are embedded.
- Require a coverage manifest for every selected month from January 2026 onward, including future years. October 2026 onward additionally requires the accrual fingerprint and per-branch review checks below. Historical manifests retain their existing contract; their fingerprints do not prove salary immutability. The stronger expected registry is not retroactively required for January–September.
- Ordinary source purchases and management salaries keep their existing period-specific allocation methods. Reviewed pools use their explicitly approved net-bank allocation basis, independently for each operation month. All-network denominators remain independent of the display branch filter.
- UI, charts and shared print/PDF rendering do not reconstruct numeric net/margin when the canonical calculation is blocked. Recorded revenue and expenses remain inspectable, with coverage explanations.
- The build runs 22 financial regression scripts in addition to its previous checks.

## Evidence contract additions (no database/schema writes)

For coverage manifests from `2026-10` onward:

- `accrualInputsFingerprint`: generated by `accrualInputsFingerprint(input, month)`. It binds salary-period IDs, employee IDs, historical period branch, gross amount, service amounts and the referenced employees' current branch/position used by the established allocation policy. Payment/advance changes and current salary rates are not accrual changes.
- `reviewChecks`: exactly one entry per relevant branch and category `payroll`, `dsmf`, `partner_fee`, `other`, with `branchId`, `category`, `status: "verified"`, nonempty `approvalRef` and `sourceRef`. These human review flags are necessary but never sufficient: the independent expectedCoverage registry below must also match exactly. Runtime never generates this registry from loaded rows.
- Existing `inputsFingerprint`, `expectedScopes`, `holds`, approvals and component validation remain required. A fingerprint only proves unchanged recorded inputs, not accounting truth.

`expectedCoverage` is mandatory from October 2026. Contract version 2 requires `month`, `status: "verified"`, `approvalRef`, and `source: {fileId, readAt, cells}`. The independent source review supplies four roster/component arrays below and three ordinary-source arrays described later; every entry has a nonempty, unique `sourceKey` within that array:

- `branches`: `{id, sourceKey, status, reason, revenueIds, expenseIds}` for every branch in the loaded catalogue, including inactive branches. Catalogue identity and each month's exact revenue/expense ID multisets must match. The monthly status is explicitly `operating`, `expense_only` or `excluded`; it is never inferred from is_active. Operating branches require observed revenue rows. Expense-only branches require costs, no revenue and a reason. Exclusions require a reason and no source revenue/costs. Empty arrays explicitly represent no source rows; missing entries do not mean zero. Expense-only status does not itself authorize suppressing expenses or change existing closed-period accounting/presentation decisions.
- `payroll`: `{sourceKey, id, employee_id, branch_id, salary_month, salary_gross, employeeBranchId, employeePosition}`. Period IDs, expected person mappings, branch, first day of the exact month, finite nonnegative numeric gross, and allocation-relevant employee metadata must match the entire month's loaded payroll. A replacement with another existing employee ID is rejected. No current rate or payout balance substitutes for gross.
- `centralPayroll`: `{sourceKey, reason, periodIds}` explicitly covers the payroll rows whose period branch_id is null. It must match both actual and expected period IDs; the existing management allocation rule is unchanged.
- `service`: `{sourceKey, branch_id, month, staff_cost_amount}`; exact branch/month identities and numeric accrued amounts, including recorded zeros.
- `components`: `{sourceKey, scope, componentKey, action, category, branchId, amount}`; exact reviewed component identity, intended action/category/branch and amount (`null` for actions without an amount). Changing a DSMF amount and its recomputed source amount together still fails against the independently approved expectation.

Missing/invalid registries and each coverage mismatch have distinct blocking reasons. The registry is a prepared source expectation, not an automatic identity resolver: an initially incorrect independently approved mapping cannot be disproved without primary evidence. Existing records lacking this registry remain blocked. No real registry/mapping/amount is created by the code or these synthetic tests.

Mandatory `expectedScopes` now dispatch by kind and version: component adjustments and branch statuses require v2 and their actual component/status validation (including adjustment conflicts); bank evidence permits v2/v3/v4 and invokes its bank validator with the configured rate. Unsupported versions/kinds, duplicates, mismatched months, stale target proofs and invalid bank entries block coverage. The caller must supply the configured bank rate when a required bank scope exists.

Bank evidence version 4 uses `bankInputsFingerprintV4(input, month)`, binding all monthly revenue and daily expenses (potential fee collisions), excluding supplier purchases and their item detail. Without an expenseScope it still fingerprints ALL daily expenses, preserving existing v4 proofs exactly. All existing approval, rate, expected revenue row, commission policy and overlap checks remain. Versions 2 and 3 retain their exact old validation: stale v3 evidence is NOT converted to v4. Creating v4 evidence requires a fresh review of the bank basis and expense overlap. No evidence records are written by this patch.

An optional `expenseScope` opts v4 into a separately reviewed, narrow exclusion policy. It requires version 1, exact month, verified status, approvalRef and source `{fileId, readAt, cells}`. Each `nonBankRows` entry requires a unique sourceKey, `nature: "exclusive_non_bank"`, `amountPolicy: "variable_nonnegative"` and an expectedRow pinning ID, branch, date, category ID/name, custom category and comment. Explicit bank/fee-purpose signals cannot be excluded. Only changes to a nonnegative amount or removal of these specifically reviewed rows are irrelevant to bank evidence. Purpose/category/branch/date changes, duplicate identities and malformed amounts reject the scope. ALL new or unreviewed expenses remain fingerprinted; no category/name heuristic automatically declares an expense unrelated. The scope itself is bound into a domain-separated fingerprint. Old v4, v2 and v3 hashes are not reinterpreted. Scope creation requires independent primary-source review; this code writes no scope records.

Consequently, bank evidence can survive an approved unrelated rent amount update, while the complete profitability manifest still needs review because total expenses changed. Unknown new expenses may still conservatively invalidate bank evidence. This is an intentional residual limitation, not a claim that every unrelated edit is automatically understood.

Historical compatibility is conditional, not blanket numeric parity: positive gross with active employee metadata retains the old result in Jan–Sep fixtures. Missing/null/blank gross and absent accruals fail closed; zero gross with positive net now explicitly raises `historical-payroll-basis-review-required` instead of silently restating a closed month. Genuine gross/net zero remains zero. For Jan–Sep, allocation metadata retains the deployed active-only eligibility: inactive employees can be resolved by ID/name but their current branch/manager position cannot alter the historical direct/pool classification. Fixtures cover both period branch present (direct) and period branch absent (pool) for all nine months. No blanket numeric parity with live historical financial data is claimed. The former current-rate estimate fallback is not restored. Resolution of these historical differences requires a separately reviewed source/closed-period decision; no override is invented here.

The former seven-header limit across an entire selected range is removed. The existing v3 per-evidence goods validation is preserved, and item queries use bounded ID batches with pagination.

## Unresolved data and release gates

The patch does not establish the October final profit. Missing/inconsistent payroll identities, DSMF and Partner Fee coverage, possible bank-fee duplication, mixed payments, and purchase discrepancies require source evidence. In particular, the supplied Sheets/RMS payroll difference and the supplier purchase difference are not automatically corrected, merged by similar names/amounts, or converted into adjustment amounts.

Existing October evidence will remain held until refreshed with the additional coverage proof. Changing a referenced employee's branch/position invalidates future coverage and requires review; this patch does not add a historical employment-role schema or change management allocation rules. Finance/Dashboard and the separate expense report retain their existing calculations; this patch targets the profitability report and its shared print output.

Safe release sequence:

1. Review this diff and run `npm run build` on the exact candidate commit. There is no configured lint script. The checked-in tests use synthetic fixtures and local database tests; no production financial queries are run by this patch.
2. In a separately authorized read-only authenticated preview, inspect September, October, a mixed range, year rollover, all branches and a single branch. Check that missing/stale coverage blocks results, that known expense details remain visible, and that print output agrees. Live authenticated browser verification is not included here.
3. Resolve source identities, missing components and ambiguous expense overlaps through the existing review process. Any financial data/evidence writes require separate authorization. Do not remove guards to force a number.
4. Obtain separate production approval. Deploy only the reviewed commit, then repeat the read-only month/branch/print checks. Roll back the deployment if needed; this patch needs no database rollback.

## Independent ordinary source coverage (registry version 2)

October 2026 onward now requires `expectedCoverage.version: 2`. Version 1 fails closed rather than being silently upgraded. In addition to the roster, each registry contains `revenue`, `expenses`, and `purchases` arrays. Every entry requires a unique `sourceKey`, nonempty `sourceCells` within the independently reviewed root source, and `expectedRow` with every field listed in `ordinaryCoverageFields`. Amounts must be explicit finite numbers in evidence; missing/blank/boolean target amounts cannot become zero. Signed amounts remain permitted: no new accounting sign policy is imposed.

Revenue pins date, branch, three channel amounts, import provenance and comment. Expenses pin date, branch, amount, category ID, custom category, joined category name and comment. Purchases pin date, branch (including null/warehouse), supplier identity/name, invoice, total, comment and deletion timestamp. Exact identity sets and values must match, so refreshing current-input fingerprints cannot excuse missing purchases or same-ID amount/classification changes. Branch revenue/expense ID lists remain a separate membership check.

The paginated purchase read now includes deleted rows in `supplierPurchaseRows` solely for coverage. Calculation, adjustments and existing fingerprints still receive only active `supplierPurchases`, preserving the deployed soft-delete treatment. Each expected purchase requires `disposition: active` when deleted_at is null, otherwise `disposition: deleted` plus a nonempty source-backed exclusion reason. Removing a deleted row, resurrecting it, changing its amount or deleting an active row without an independently updated registry blocks coverage. No target-derived production registry is generated. Synthetic fixtures explicitly generate test-only evidence before mutations.

`resolveProfitabilityPayrollAllocation` is shared by the loader and branch disposition validation. It preserves period branch fallback to employee branch, the exact existing manager-position aliases, and Jan–Sep active-only metadata eligibility. A null-period active cook whose employee branch is B therefore incurs direct costs at B; B cannot be excluded as cost-free. A manager's payroll remains a revenue-share pool, including when their employee branch is set. `centralPayroll` denotes null-period source rows, not necessarily management pool membership.

Validation includes 19 target mutations with all fingerprints refreshed and expected sources unchanged, duplicate identities rejected before fingerprint refresh, explicit deleted-exclusion tests, and full-loader branch allocation assertions. Primary-source accuracy of a newly approved registry still requires human/source review: agreement with an incorrectly approved independent registry cannot establish the real-world truth.
