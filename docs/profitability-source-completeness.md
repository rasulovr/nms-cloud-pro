# Profitability source completeness

Prepared against production commit `9d151045db9af0db5b25e5b824be6f653b631ca6`, deployment `dpl_AyvKpX9edsBYsx3AP9h1jW5hgvyF` (app.rms.rest). This patch changes reporting code only. No migration, data reconciliation, setting change, deployment, or automatic evidence conversion is included.

## Behavior

- Read salary periods, employees (including inactive employees), and service charge with stable pagination. Errors, null responses, and exhausted read limits fail the report instead of returning partial totals.
- Use salary_gross only in the profitability report. Observed zero stays zero; net balances, advances, payments, current salary rates and official-day estimates cannot substitute for accruals. Employee/period identities and duplicate employee-month rows are checked. The existing management allocation policy remains in place.
- Consume reviewed component records for every selected month. DSMF is an explicit supported branch component, alongside Partner Fee. Existing provenance, identity, collision, duplicate, and stale-input checks still apply. No inferred employee matching or October amounts are embedded.
- Require a coverage manifest for every selected month from January 2026 onward, including future years. October 2026 onward additionally requires the accrual fingerprint and per-branch review checks below. Historical manifests retain their existing contract; their fingerprints do not prove salary immutability.
- Ordinary source purchases and management salaries keep their existing period-specific allocation methods. Reviewed pools use their explicitly approved net-bank allocation basis, independently for each operation month. All-network denominators remain independent of the display branch filter.
- UI, charts and shared print/PDF rendering do not reconstruct numeric net/margin when the canonical calculation is blocked. Recorded revenue and expenses remain inspectable, with coverage explanations.
- The build runs 20 financial regression scripts in addition to its previous checks.

## Evidence contract additions (no database/schema writes)

For coverage manifests from `2026-10` onward:

- `accrualInputsFingerprint`: generated by `accrualInputsFingerprint(input, month)`. It binds salary-period IDs, employee IDs, historical period branch, gross amount, service amounts and the referenced employees' current branch/position used by the established allocation policy. Payment/advance changes and current salary rates are not accrual changes.
- `reviewChecks`: exactly one entry per relevant branch and category `payroll`, `dsmf`, `partner_fee`, `other`, with `branchId`, `category`, `status: "verified"`, nonempty `approvalRef` and `sourceRef`. This is a human-reviewed completeness attestation, including genuine zero/not-applicable components and roster reconciliation; row presence is not proof of completeness. A known employee ID cannot detect that an importer attached the wrong person to a spreadsheet row. Such cases must remain held until the source roster is reconciled.
- Existing `inputsFingerprint`, `expectedScopes`, `holds`, approvals and component validation remain required. A fingerprint only proves unchanged recorded inputs, not accounting truth.

Bank evidence version 4 uses `bankInputsFingerprintV4(input, month)`, binding all monthly revenue and daily expenses (potential fee collisions), excluding supplier purchases and their item detail. All existing approval, rate, expected revenue row, commission policy and overlap checks remain. Versions 2 and 3 retain their exact old validation: stale v3 evidence is NOT converted to v4. Creating v4 evidence requires a fresh review of the bank basis and expense overlap. No evidence records are written by this patch.

The former seven-header limit across an entire selected range is removed. The existing v3 per-evidence goods validation is preserved, and item queries use bounded ID batches with pagination.

## Unresolved data and release gates

The patch does not establish the October final profit. Missing/inconsistent payroll identities, DSMF and Partner Fee coverage, possible bank-fee duplication, mixed payments, and purchase discrepancies require source evidence. In particular, the supplied Sheets/RMS payroll difference and the supplier purchase difference are not automatically corrected, merged by similar names/amounts, or converted into adjustment amounts.

Existing October evidence will remain held until refreshed with the additional coverage proof. Changing a referenced employee's branch/position invalidates future coverage and requires review; this patch does not add a historical employment-role schema or change management allocation rules. Finance/Dashboard and the separate expense report retain their existing calculations; this patch targets the profitability report and its shared print output.

Safe release sequence:

1. Review this diff and run `npm run build` on the exact candidate commit. There is no configured lint script. The checked-in tests use synthetic fixtures and local database tests; no production financial queries are run by this patch.
2. In a separately authorized read-only authenticated preview, inspect September, October, a mixed range, year rollover, all branches and a single branch. Check that missing/stale coverage blocks results, that known expense details remain visible, and that print output agrees. Live authenticated browser verification is not included here.
3. Resolve source identities, missing components and ambiguous expense overlaps through the existing review process. Any financial data/evidence writes require separate authorization. Do not remove guards to force a number.
4. Obtain separate production approval. Deploy only the reviewed commit, then repeat the read-only month/branch/print checks. Roll back the deployment if needed; this patch needs no database rollback.
